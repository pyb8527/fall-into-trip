## 1. 글자에서 금액 · 날짜 · 가게 뽑기 — **찬성** (1차, 뼈대)

### 이미 있는 것
- 기기 안에서만 글을 읽어 칸을 채우는 틀: `lib/intent.web.ts:226` `parseBooking` — **못 읽으면 `null`, 서버로 넘기지 않음**, 화면은 칸을 그대로 둠.
- 지출 칸: `Expense` — 날짜(`dayId`) · 분류(`cat`) · 이름 · 금액 · 통화 · 결제 수단(`pay`) (`expense/domain/Expense.java:32-74`)
- 공개 규칙 파서 중 한·일 영수증에 맞는 것은 **없음**(`survey.md` 7).

### 붙는 자리
새 `lib/receipt.ts`(순수 셈) → 2번(붙여넣기)과 3번(OCR)이 같이 씀 → `SpendSheet`(`app/money/[id].tsx:1086`) 칸에 채움

### 걸리는 것
- **돈은 껄끄러움을 없애는 자리** — 틀린 합계가 그대로 저장되면 정산이 틀리고, 그 다툼이 가계부 탓이 됩니다. 조사의 불평 1위가 "합계를 확신 있게 틀림"이었습니다(`survey.md` 13).
- **사람이 수락해야 바뀝니다** — 저장은 사람이 누릅니다.

### 고쳐 받는다면
- 일본: 합계 후보 `合計` → `税込合計` → `お買上計`. **빼는 줄** `小計` · `お預り` · `お釣り` · `(内消費税)` · `対象計`. 날짜 `令和N年` · `YYYY/MM/DD` · `YYYY年M月D日`.
- 한국: 합계 후보 `받을금액` · `합계` · `결제금액` · `승인금액`. **빼는 줄** `부가세` · `과세물품가액` · `면세` · `받은금액` · `거스름돈`.
- **검산이 맞을 때만 금액을 채웁니다.** `お預り − お釣り = 合計`, `小計 + 消費税 = 合計` 처럼 두 줄 이상이 서로 맞으면 "확인됨", 하나만 있으면 "확인 안 됨"으로 채우고 칸 옆에 표시합니다. 후보가 둘 이상 갈리면 **금액 칸을 비워 둡니다** — 틀린 숫자보다 빈칸이 낫습니다.
- 가게 이름은 맨 위 몇 줄 중 숫자 · 주소 · 전화가 아닌 첫 줄. 확신이 없으면 비웁니다.
- 날짜는 여행 날짜 안에 들 때만 그 날(`dayId`)로. 밖이면 비웁니다.

## 3. 기기 안 OCR 로 사진에서 칸 채우기 — **조건부 찬성** (1차, 실측 뒤)

### 이미 있는 것
- 사진 고르기: `lib/pick-photo.web.ts` — 지금은 고르고 **올리는**(`pickAndUpload:72`) 것만 밖에 냅니다. 안쪽의 `pick()` 는 이미 고르기만 합니다.
- 카메라 · 앨범은 앱(웹뷰)에서도 이 길로 돕니다(피드 사진이 이미 씀).

### 붙는 자리
`SpendSheet` 에 "영수증 찍기" → `pick()`(올리지 않음) → 새 `lib/ocr.web.ts`(워커) → 글자 → `lib/receipt.ts` → 칸

### 걸리는 것
- **읽기용 그림을 서버에 받지 않습니다** — 그림은 기기를 떠나지 않습니다. OCR 도 기기에서.
- **남의 서버를 부르지 않습니다** — 모델을 CDN 에서 받으면 쓰는 사람이 그쪽에 남습니다. Pretendard 처럼 **우리 서버(`public/`)에서** 내보냅니다(`src/global.css` 머리 주석과 같은 판단).

### 고쳐 받는다면 — 엔진은 실측으로 고릅니다

| | PaddleOCR(PP-OCRv5 mobile) | Tesseract.js(fast) |
|---|---|---|
| 처음 받는 양(한 + 일) | 약 35MB | 약 4MB |
| 한국 감열지 단어 정확도(KORIE, 2차) | 73.3% | 64.7% |
| 라이선스 | Apache-2.0 | Apache-2.0 |
| 걱정 | 공식 SDK 가 `korean` · `japan` 을 받는지 미확인, 2025-12 "브라우저에서 안 됨" 보고 | 감열지 · 일본어에 약함 |

**실측**: 일본 영수증 5장 · 한국 영수증 5장 · CORD 테스트 몇 장을 iPhone 1대 · 중급 안드로이드 1대 웹뷰에서 두 엔진으로 돌려, **한 장 시간 · 합계가 맞았는가(1번 규칙 뒤)** 를 표로 남깁니다.
- PaddleOCR 이 폰에서 돌고 합계 정확도가 눈에 띄게 높으면 PaddleOCR.
- 아니면 Tesseract.js.
- **둘 다 합계를 반 넘게 틀리면 3번을 닫고 2번(붙여넣기)만 둡니다.**

모델은 **처음 "영수증 찍기"를 누를 때** 크기를 말하고 받습니다(어디 갈지 물어보기의 1GB 받기와 같은 방식, `lib/intent.web.ts:111` `fetchModel`). 받은 뒤에는 기기에 담아 둡니다.

### 값

| | |
|---|---|
| 새 외부 의존 | `@paddleocr/paddleocr-js` + `onnxruntime-web`, **또는** `tesseract.js` (실측으로 하나) |
| 구글 호출 | 0 |
| 서버 저장 | 0 — 사람의 그림은 안 받음. 모델 파일만 `public/ocr/` 에 정적으로(4~35MB) |
| EAS 재빌드 | 필요 없음 |
| 스키마 변경 | 없음 |
| 백엔드 변경 | 없음 (nginx 캐시 정책에 `/ocr/` 한 줄) |

### 지켜야 할 것
- 기본은 **단일 스레드 WASM**, WebGPU 는 쓰지 않습니다(iOS 웹뷰 충돌 보고, `survey.md` 6).
- 읽는 동안 화면이 멈추지 않게 워커에서.
- 모델 출처 · 라이선스를 `public/ocr/LICENSES.txt` 에.

## 6. 기기 안 LLM 으로 다듬기 — **재설계 권장** (1차)

### 이미 있는 것
- 같은 일을 하는 자리: `parseBooking`(`lib/intent.web.ts:226`) — 크롬 내장 모델 또는 WebLLM, JSON 스키마로 출력 강제(`:259`), 모델이 준비 안 됐으면 `null`.

### 걸리는 것
- **아는 것만 말합니다** — 작은 모델은 값을 정확히 맞히는 데 약합니다. 3B 모델에서 모든 칸이 맞는 비율이 0.20 이었고, 합계는 정규식(0.80)이 3B 보다 나았습니다(`survey.md` 8). FIT 의 모델은 1.5B 입니다.

### 고쳐 받는다면
- **금액 · 통화 · 날짜는 LLM 에 맡기지 않습니다.** 1번 규칙만 씁니다.
- LLM 은 **가게 이름과 분류(`cat`)** 만 채웁니다. 그것도 **모델이 이미 준비된 사람에게만**(`intentState() === 'ready'`). 영수증 하나 때문에 1GB 받기를 권하지 않습니다.
- LLM 이 금액을 내놓으면 버립니다(스키마에 금액 칸을 두지 않음).

### 값
모두 없음. 새 의존 없음(이미 있는 모델).

## 7. 품목 나누기 — **반대** (지금은)

**이것을 받으면 지출의 모양이 값을 치릅니다.** 지금 지출은 금액 하나에 나눌 사람 목록입니다(`Expense.share`). 품목마다 사람을 배정하려면 지출 아래에 품목 표가 생기고(스키마), 정산 셈(`SettlementCalculator`)이 품목을 알아야 합니다.
게다가 품목 줄은 합계 한 줄보다 훨씬 많이 틀립니다(Splitwise Pro 의 "품목을 못 읽는다" 불평, `survey.md` 13).
"안 먹은 사람까지 나눈다"는 불편은 지금도 **나눌 사람을 골라** 풉니다(`money/[id].tsx:646-669`). 합계 읽기가 먼저 자리 잡은 뒤 다시 봅니다.

## 8. 영수증 사진을 지출에 붙여 보관 — **반대**

**이것을 받으면 사진 자리가 값을 치릅니다.** 지출마다 사진이 붙으면 사람당 1000장(`PhotoService.java:66`) 한도를 영수증이 먹고, 서버 옆 폴더 하나의 용량을 같이 씁니다. 지출에는 사진 칸도 없습니다(`Expense.java`).
조사에서 사진만 붙이는 앱(Tricount 등)이 많았지만, FIT 가 하려는 것은 **읽어서 채우는 것**이고 그 그림은 기기를 떠날 이유가 없습니다.

## 9. 서버에서 읽기 — **반대**

`docs/2026-10/verdict.md:107` 그대로입니다. 서버에서 읽으면 **사람이 남기려고 올린 것이 아닌 그림**을 받는 문이 생깁니다. 영수증에는 카드 뒷자리 · 승인번호가 찍혀 있습니다 — `parseBooking` 이 서버로 미끄러지지 않는 것과 같은 이유입니다.

## 10. 그림을 바로 JSON 으로 (Donut 등) — **반대**

Donut(CORD)은 인도네시아 영수증으로만 배웠고 한·일에는 다시 가르쳐야 합니다. 브라우저 판이 약 220MB 입니다. Florence-2 는 영어 중심, LayoutLMv3 는 비상업 라이선스입니다(`survey.md` 4).

## 11. 멀티스레드 WASM (COOP/COEP) — **반대**

**이것을 받으면 바깥 스크립트가 값을 치릅니다.** 멀티스레드 WASM 에 필요한 COOP/COEP 헤더는 페이지 전체에 걸립니다. 그러면 구글 지도 · 카카오 SDK 같은 다른 출처의 스크립트 · 그림이 막힐 수 있습니다(지금 `nginx.conf` 에는 이 헤더가 없습니다). 영수증 한 장은 단일 스레드로 충분한지 3번 실측에서 봅니다.

- **품목 나누기** — 지출에 품목 표가 생기고 정산이 품목을 알아야 함. 품목 줄은 더 많이 틀림
- **영수증 사진 보관** — 사진 한도와 서버 용량을 영수증이 먹음
- **서버에서 읽기** — 읽기용 그림을 받는 문. 카드 뒷자리 · 승인번호
- **Donut 등 그림 → JSON** — 한·일 미학습, 220MB
- **멀티스레드 WASM** — 페이지 전체 헤더가 바깥 스크립트를 막을 수 있음

## 아직 모르는 것

- **폰 웹뷰에서 한 장 읽는 시간과 합계 정확도.** 두 엔진 모두 실측 전입니다. 3번의 조건이 이것입니다.
- **PaddleOCR 공식 SDK 가 한국어 · 일본어 모델을 받는지**, 받지 않으면 커뮤니티판(`ppu-paddle-ocr`)으로 갈지.
- **모델 35MB 를 처음 받는 것**이 폰에서 얼마나 걸리는지, 웹뷰가 이만한 파일을 기기에 담아 두는지(Cache Storage / IndexedDB).
- **iOS 웹뷰의 메모리** — onnxruntime-web 이 큰 사진 한 장에 메모리를 얼마나 쓰는지. 긴 변을 몇 px 로 줄일지.
- 규칙이 놓치는 양식(편의점 · 자판기 · 택시 · 면세점 영수증). 2번을 먼저 내서 실제 붙여 넣은 글로 늘려 갑니다.
- 한·일 영수증 시험 데이터 — JaWildText 는 공개 예정, 한국 데이터는 라벨 유무 불명. 우선 직접 모은 표본으로 시작합니다.
