# 붙여 넣은 글에서 장소를 뽑아 보석함에 — 기기 안에서, 사람이 골라서

> `verdict.md` 1번에서 **재설계 권장 · 1차(관문 있음)**으로 받은 것의 실행 계획입니다.
> 아직 코드는 한 줄도 바뀌지 않았습니다.
>
> **관문이 먼저입니다.** 같은 모델에 같은 종류의 일을 시킨 예약 붙여 넣기가
> 「모델이 해내는지 안 재 봤습니다」 로 멈춰 있습니다(`docs/2026-09/plan-booking-paste.md`
> §10). 이 계획의 1단계는 코드가 아니라 그 측정입니다(§8). 못 넘으면 이 계획은
> 접고, **서버로 글을 보내 뽑는 길로 메우지 않습니다.**
>
> 백엔드는 한 줄도 안 바뀝니다. 웹에 올리면 안드로이드 앱에도 들어가지만, 앱 안
> 웹뷰에서 모델이 도는지는 아직 모릅니다(§9).

## 1. 하려는 것

지금은 **한 곳씩 다시 찾습니다.**

블로그 글 「오사카 2박 3일 먹방 — 이치란 도톤보리점, 551 호라이, 쿠로몬 시장…」,
인스타 캡션, 단톡에서 친구가 적어 준 「여기 여기 가 봐」. 사람이 보석함에 담으려면
지금은 이렇게 합니다.

```
글을 보고 이름 하나를 외움 → FIT 보석함 → 「담기」 → 장소 찾기에 적음
→ 결과에서 맞는 곳을 고름 → 다시 글로 돌아가 다음 이름 …
```

열 곳이면 열 번 왕복입니다. 조사에서 가장 출처가 고르게 많은 불평이 이 자리였습니다
(`survey.md` 「눈에 띈 것」 첫 줄 — Tripsy · Mindtrip · 릴스 전용 앱 · HN).

## 3. 버리는 것

### 3.1 링크를 넣으면 서버가 글을 읽어 오기 — 버립니다

인스타 · 틱톡 · 블로그 주소만 받고 서버가 그 글을 긁어 오는 모양입니다. 로그인 벽과
약관 문제이고, 조사도 무엇으로 읽는지 확인 못 했습니다(`survey.md` 1번 「확인 못 한
것」). 사람이 글을 **복사해 붙여 넣는** 것만 받습니다. 붙여 넣은 칸에 주소만 있으면
「글이 없어 장소를 뽑을 수 없어요. 본문을 복사해 붙여 넣어 주세요」 한 줄로 답합니다.

### 3.2 스크린샷 읽기 — 버립니다

서버에서 읽으면 남기려고 올린 것이 아닌 그림을 받는 새 문입니다(`PhotoService.java:66`
의 한도는 사람이 올린 사진의 것). 기기에서 읽으면 OCR 이 새 네이티브 의존이고,
`docs/2026-09/verdict.md` 2번이 같은 이유로 버렸습니다.

### 3.3 구글 · 애플 지도 목록 가져오기 — 버립니다

공개 API 가 없습니다(`verdict.md` 1번).

### 3.4 저절로 담기 — 버립니다

뽑은 곳을 바로 보석함에 넣지 않습니다. 판에 늘어놓고 **사람이 고른 것만** 담습니다.
모델이 「점심」 을 가게 이름으로 뽑거나 구글이 다른 도시의 같은 이름을 찾으면, 저절로
담는 순간 보석함에 엉뚱한 곳이 쌓이고 사람은 자기가 안 한 것을 지워야 합니다
(「사람이 수락해야 바뀝니다」, `trip/domain/RouteTidy.java`).

### 3.5 모델이 없을 때 서버로 글 보내기 — 버립니다

붙여 넣은 글은 남의 블로그 본문이거나 단톡 대화입니다. 거기에는 남의 이름과 전화번호가
섞입니다. **모델을 쓸 수 없는 기기(`canParseHere === false`)에서는 단추를 안 냅니다.**
예약 붙여 넣기가 세운 줄과 같습니다(`plan-booking-paste.md` §3.5).

### 3.6 일정에 바로 넣기 — 버립니다 (이번에는)

보석함까지만 갑니다. 일정으로 옮기는 길은 이미 있습니다 — `SavedPlaceService.pour`
(`:155`, `POST /api/days/{dayId}/places/from-saved`). 판에 「어느 날에」 를 더하면
날 고르기 · 권한 · 판 두 겹이 한꺼번에 붙습니다.

### 3.7 비슷한 곳을 대신 골라 주기 — 버립니다

검색이 빈손이면 「못 찾았어요」 로 남깁니다(`verdict.md` 1번 「지켜야 할 것」). 그 줄에
「직접 찾기」 를 두어 사람이 이름을 고쳐 다시 찾게 합니다.

## 4. 갈 곳

```
[사람]  블로그 · 캡션 · 단톡 글을 복사
          |
          v
  보석함 → 「담기」 판 → 「붙여 넣은 글에서 찾기」         ← canParseHere 일 때만 보임
          |   (판을 닫고 새 판을 엽니다. 겹치지 않습니다)
          v
  PastePlacesSheet  — 칸 하나 + 「찾기」
          |
          | intentState() 가 'ready' 가 아니면 → 「이 기기에서 글을 읽을 모델을 켜요」
          |    + modelNote() 한 줄 + 「켜기」(fetchModel, 진행 막대)
          v
  parsePlaces(text)                         ← 기기 안. 글은 밖으로 안 나갑니다
          |   lib/places-prompt.ts 의 PROMPT · SHOTS · PLACES_SCHEMA · readPlaces
          v
  { area: "오사카" | null, names: ["이치란 도톤보리점", "551 호라이", …] }
          |
          |  readPlaces 가 거르는 것:
          |   · 원문에 글자 그대로 없는 이름은 버림   ← 지어낸 이름을 여기서 막습니다
          |   · 같은 이름 두 번은 하나로
          |   · 10개에서 자름
          |
          +-- 하나도 없으면 → 「장소 이름을 찾지 못했어요」. 칸은 그대로
          v
  이름마다  GET /api/places/search?q=<이름> <area>      ← 서버로 가는 것은 이 검색어뿐
          |   셋씩 차례로. 429 가 오면 거기서 멈추고 「장소를 너무 자주 찾았어요…」
          |   (GoogleQuotaFilter 의 문구 그대로)
          v
  판에 줄마다 나란히:
     「뽑은 말」          「구글이 찾은 곳」 (첫 결과 · 주소 한 줄)     [✓]
     이치란 도톤보리점     이치란 도톤보리점 본관 · 오사카시 주오구…      ✓
     쿠로몬               못 찾았어요 · 직접 찾기                       –
     (이미 담은 곳이면 「이미 담겨 있어요」, 체크 없음)
     (두 이름이 같은 구글 번호로 가면 한 줄로)
          |
          | 기본은 찾은 것 모두 체크. 사람이 끄고 켭니다
          v
  [사람]  「n곳 담기」
          |
          v
  POST /api/saved  × 고른 수 (차례로)   ← 지금 장소 찾기에서 담을 때와 같은 몸통
          |   300개가 차면 거기서 멈추고 「n곳 담았어요. 보석함이 가득 찼어요」
          v
  invalidate 가 'saved' 를 알림 → 보석함 목록이 스스로 다시 읽음
```

**검색어에 지역을 붙이는 이유** — 장소 찾기 칸이 이미 「지역을 함께 쓰라」 고 힌트를
줍니다(`place-search.tsx` 의 `Field` 위 주석). 「이치란」 은 세계에 수십 곳입니다. 글에
「오사카」 가 있으면 모델이 `area` 로 뽑고, 원문 확인을 같은 규칙으로 거칩니다.

**「원문에 그대로 있는 이름만」** — 예약 붙여 넣기에는 없던 막이 여기서는 됩니다.
뽑을 것이 원문 속 **글자 조각**이기 때문입니다. 띄어쓰기 · 대소문자만 맞춰 보고
부분 문자열이 아니면 버립니다. 모델이 이름을 번역하거나 다듬으면 그것도 버려지는데,
지어낸 것을 들이는 것보다 하나 놓치는 쪽을 고릅니다.

## 8. 순서와 의존

1. **관문 — 모델이 해내는지 잽니다.** 코드보다 먼저입니다.
   - 실제 글 열 편을 모읍니다: 블로그 본문 넷, 인스타 캡션 셋, 단톡 메시지 셋.
   - 웹(크롬 내장 또는 WebLLM 1.5B)에서 같은 프롬프트로 돌립니다. 판 없이 콘솔로
     충분합니다.
   - 셉니다: 글마다 실제 장소 수 · 뽑은 수 · 그중 장소가 아닌 말(「점심」, 「오사카」) ·
     원문 확인으로 버려진 것 중 진짜였던 것.
   - **접는 기준(실측 전에 정해 둠)** — 장소가 아닌 말이 뽑은 것의 절반을 넘는 글이
     열 편 중 셋 이상이거나, 실제 장소의 절반도 못 뽑는 글이 다섯 이상이면 접습니다.
     지어낸 이름은 원문 확인이 막으므로 기준에 넣지 않았습니다.
   - 그 김에 예약 붙여 넣기의 관문(`plan-booking-paste.md` §10)도 같은 모델로 잽니다.
2. **`lib/places-prompt.ts` 와 `PastedPlaces`** — 1에서 쓴 프롬프트를 그대로 옮깁니다.
3. **`intent.web.ts` 의 `parsePlaces`**, `intent.ts` 의 자리 맞춤.
4. **`paste-places-sheet.tsx`** — 모델 켜기 → 뽑기 → 검색 → 나란히 → 담기.
5. **`saved.tsx` 의 단추.**

뒤에 서는 것 — `plan-share-in.md` 가 4번 판을 그대로 씁니다. 이 계획이 접히면 그
계획도 접힙니다.

## 9. 아직 모르는 것

- **모델이 블로그 글에서 장소 이름을 얼마나 고르게 뽑는지.** §8 의 1번입니다.
  1.5B 와 0.5B(`intent.web.ts:69-71`, 기기 메모리 8GB 미만이면 작은 쪽)가 다를
  것이라 둘 다 봐야 합니다.
- **안드로이드 웹뷰에서 `canParseHere` 가 참인지.** 앱은 웹을 띄웁니다. 웹뷰에 크롬
  내장 모델은 없을 가능성이 크고, WebGPU 가 열려 있는지는 재 보지 않았습니다. 거짓이면
  **앱에서는 단추가 안 뜨고** 이 기능은 브라우저에서만 됩니다. `verdict.md` 「아직
  모르는 것」 둘째 줄과 같은 물음입니다.
- **모델 켜기가 이 판에서 견딜 만한지.** `intentState()` 는 페이지를 새로 열 때마다
  `'absent'` 로 돌아갑니다(`intent.web.ts:84-86`). 그래서 판을 열 때마다 「켜기」 를
  한 번 눌러야 할 수 있습니다. 받은 것은 브라우저가 두므로 두 번째부터는 받지 않고
  올리기만 하는데, 그 시간이 얼마인지 모릅니다. 같은 까닭으로 지금 `BookingPaste` 는
  설정에서 켜고 온 사람에게만 보입니다(`trip/[id].tsx:4629`).
- **`area` 를 하나로 둘지.** 「오사카 · 교토 2박 3일」 처럼 지역이 둘인 글이 흔합니다.
  하나만 붙이면 교토 가게가 오사카 쪽으로 기울어 찾힙니다. 이름마다 지역을 붙이게
  할지는 1번에서 실제 글을 보고 정합니다.
- **긴 글을 어디서 자를지.** 블로그 본문은 수천 자입니다. 내장 모델 · WebLLM 의 입력
  한도와 걸리는 시간을 재고 정합니다. 자르면 뒤쪽 장소를 놓칩니다.
- **원문 확인이 진짜 이름을 얼마나 버리는지.** 「551蓬莱」 를 「551 호라이」 로 옮겨
  적는 식이면 버려집니다. 많으면 원문 확인을 느슨하게(예: 이름의 앞 몇 글자) 할지
  1번에서 봅니다.
- **검색 첫 결과가 맞는 곳인지.** 판은 첫 장만 보여 줍니다. 틀리면 체크를 끄고 「직접
  찾기」 로 갑니다. 첫 장이 자주 틀리면 둘째 장까지 보여 줄지 정합니다.
