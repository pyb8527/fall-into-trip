# 대중교통만 안 나오던 것

> 쓰다가 나온 고장입니다. 조사에서 나온 것이 아닙니다.
>
> **넷을 고쳤습니다.** 진짜 원인은 **§8** 입니다 — 구글이 준 소요시간을
> 우리가 못 읽고 있었습니다. §2·§6·§7 은 그 주변에서 같이 나온 것들이고,
> 셋 다 고칠 값은 했습니다.

## 1. 무엇이 보였나

걷기와 차는 나오는데 **대중교통만 안 나오는 구간**이 있었습니다. 같은 구간을
구글 지도 앱에서 찾으면 나옵니다.

## 2. 확실한 원인 — 언제 타는지를 안 보냈습니다

`RouteService.ask()` 가 구글에 보내는 몸통에 `departureTime` 이 없었습니다.

구글 문서가 이렇게 적어 두었습니다.

> 둘 다 안 주면 `departure_time` 은 **현재 시각(now)** 으로 기본값이 잡힙니다.

그래서 **11월 일정을 새벽 두 시에 짜면 그 시각 시각표로 계산**했습니다. 그때
안 다니는 노선은 "그런 길 없음" 으로 왔습니다.

**걷기와 차는 시각표가 없습니다.** 그래서 멀쩡히 나왔고, 대중교통만 빠진
것처럼 보였습니다.

그런데 `of()` 는 **`day.getIso()` 를 이미 들고 있었습니다.** 날짜를 아는데
안 보내고 있었습니다.

## 3. 고친 것

### 3.1 그 날 그 시각으로 묻습니다

`departureFor(day, from)` 이 정합니다.

| | |
|---|---|
| 날짜 | `Day.iso` |
| 시각 | 출발하는 장소에 적어 둔 `time`. 못 읽으면 **09:00** |
| 시간대 | **경도 ÷ 15** 로 어림 |

**"점심때쯤" 은 시각으로 안 읽습니다.** 집 규칙이 자유 글자를 숫자로 읽지
말라고 합니다. 그런 자리는 낮으로 둡니다.

### 3.2 시간대를 왜 어림하는가

구글에게는 **절대 시각**을 줘야 하는데 우리는 그 나라의 시간대를 모릅니다.
좌표로 사 오는 길(Time Zone API)이 있지만 **바깥문을 하나 더 여는 일**입니다.

그래서 경도로 어림합니다. 오사카(135도)는 +9로 정확히 맞고 유럽은 한두
시간 틀립니다. **틀려도 됩니다** — 고치려는 것은 "낮에 다니는 것을 밤으로
물어서 아무것도 안 나오는 것" 이지 분 단위 정확도가 아닙니다.

### 3.3 구글이 받는 창

지금부터 **7일 전 ~ 100일 뒤**까지만 받습니다. 그 밖이면 **아예 안
보냅니다** — 보내면 요청이 거절돼서 지금보다 나빠집니다. 아주 먼 여행은
예전처럼 현재 시각으로 계산되고, 그건 원래 하던 대로입니다.

경계에서 미끄러지지 않게 5일 / 95일로 줄여 잡았습니다.

### 3.4 캐시 열쇠에 시각을 넣었습니다

**이걸 빠뜨리면 고친 것이 도리어 해가 됩니다.** 열쇠가 `(수단, 좌표, 좌표)`
뿐이라, 11월 1일 아침과 11월 3일 밤이 같은 칸을 쓰고 먼저 물은 쪽의 답이
다른 날에도 나옵니다.

### 3.5 안 건드린 것

| | 왜 |
|---|---|
| 걷기·차 | 시각표가 없습니다. 차에 붙이면 그 시각의 교통량으로 계산이 바뀌는데, 이 결함과 상관없는 다른 변화입니다 |
| "지금 여기서"(`fromHere`) | 정말 지금입니다. 구글이 현재로 잡는 것이 맞습니다 |
| 길 위에서 찾기(`pathBetween`) | 길 모양만 씁니다. 걷기로 묻고 있어 시각이 상관없습니다 |

## 4. 아직 사람이 봐야 하는 것

이것을 고쳐도 안 나오면 남은 둘 중 하나입니다.

| | |
|---|---|
| **두 곳이 너무 가까움** | 몇백 미터면 구글이 버스를 태울 이유가 없다고 봅니다. 정상입니다 |
| **지역** | 구글이 *"Functionality varies by region"* 이라고만 하고 어느 나라가 되는지는 안 밝힙니다. **여기는 단정 못 합니다** |

### 어느 것인지 아는 법

코드가 이미 이유를 남깁니다(`ask()` 의 `log.info`).

```bash
docker compose logs api | grep "경로가 비었습니다"
```

`응답=` 안이 빈 `{}` 면 거리나 지역이고, 오류 메시지가 있으면 다른 문제입니다.

## 5. 잰 것

`DepartureTimeTest` **7 통과 / 0 실패** (새로). 구글 키가 없어도 이 셈은
잽니다 — 보는 것이 "무엇을 물어보는가" 이기 때문입니다.

| 무엇을 | |
|---|---|
| 적어 둔 시각을 그 날짜에 붙이는가 | 12:30 현지 = 03:30 UTC (동경 135도) |
| 자유 글자를 시각으로 안 읽는가 | "점심때쯤" → 09:00 |
| 시간대를 경도로 어림하는가 | 런던이 오사카보다 아홉 시간 늦게 아침 |
| 창 밖이면 안 보내는가 | 200일 뒤, 60일 전 → `null` |
| **창 안이면 반드시 보내는가** | 여기서 `null` 이면 고친 것이 아무 일도 안 합니다 |

같이 돌린 것 — `./gradlew test` 34 통과(신규 7), icon 42 · trip 60 ·
recommend 30 · place 9, 전부 0 실패.

**실제로 노선이 나오는지는 못 쟀습니다.** 구글 키가 운영에만 있습니다.

## 6. 두 번째 증상 — 수단이 들쭉날쭉 빠지는 것

§2 를 고친 뒤에 다른 말을 들었습니다.

> 지금 걸어서, 택시·차 이렇게 두 개만 나오는데 **다른 장소는 대중교통만
> 나올 때도 있고** 이래

이건 §2 와 **다른 증상**입니다. §2 는 대중교통이 일관되게 빠지는 것인데,
이건 수단이 자리마다 들쭉날쭉 빠집니다.

### 6.1 수단이 사라지는 길은 둘입니다

`compare()` 가 `reachable` 아닌 수단을 목록에서 그냥 뺍니다. 그리고
`unreachable` 이 되는 경우가 둘이었습니다.

| | 로그 |
|---|---|
| 구글이 "그런 길 없음" 이라고 답함 | `경로가 비었습니다` + 구글 응답 전문 |
| **아무 오류나 남** (429·타임아웃·거절) | `경로를 받지 못했습니다` + 오류 메시지 |

**둘을 같은 값으로 돌려주고 있었습니다.** 그래서 부르는 쪽이 가릴 수
없었습니다.

### 6.2 그래서 실패가 여섯 시간 눌러앉았습니다

`leg()` 가 성공·실패를 **안 가리고** 캐시에 넣었습니다.

```java
Leg fresh = ask(from, to, mode, when);
Duration keep = mode == Mode.TRANSIT ? KEEP_TRANSIT : KEEP_STATIC;
cache.put(id, new Cached(fresh, Instant.now().plus(keep)));   // 실패도 들어갑니다
```

걷기·자동차는 `KEEP_STATIC` 이 여섯 시간입니다. **한 번 실패하면 여섯 시간
동안 그 수단이 화면에서 사라집니다.** 새로고침해도 캐시에서 같은 실패가
나옵니다. 날짜를 열 때마다 서른여섯 번을 부르니(수단 3 × 구간 12) 그중
하나쯤 미끄러지는 것은 드문 일이 아니고, 그 하나가 반나절을 갑니다.

### 6.3 고친 것

`ask()` 가 오류일 때 **`null`** 을 돌려줍니다. "그 길이 없다"(안정적인 답)와
"못 물어봤다"(사고)가 이제 갈립니다.

| | 들고 있는 시간 |
|---|---|
| 길이 없다 — 구글이 그렇게 답함 | 걷기·차 6시간, 대중교통 20분 (그대로) |
| **못 물어봤다** | **1분** |

아예 안 넣을 수도 있었지만 그러지 않았습니다. 구글이 잠깐 맛이 갔을 때
날짜를 열 때마다 서른여섯 번씩 다시 나가고, **그 실패도 문턱을 깎습니다** —
`spend` 는 나가기 전에 셉니다. 사람이 다시 열어 볼 때쯤이면 풀려 있을 만큼만
둡니다.

### 6.4 실제로 재 봤습니다

일부러 틀린 구글 키를 넣고 띄웠습니다. `enabled()` 는 켜지고 구글이
거절하므로 **실패 경로를 그대로 탑니다.** 밖으로 나갈 때마다 로그가 한 줄씩
남는 것을 세었습니다.

| | 로그 줄 |
|---|---|
| 부르기 전 | 0 |
| 한 번 열고 나서 | 1 — 나갔습니다 |
| **바로 다시 열면** | 1 — **안 나갔습니다**(캐시) |
| **1분 지나 다시 열면** | 2 — **다시 물었습니다** |

마지막 줄이 이 고침의 전부입니다. 옛 코드면 여기가 **여섯 시간 뒤**였습니다.

### 6.5 아직 안 한 것

**왜 실패하는지는 아직 모릅니다.** 이 고침은 실패가 오래 남는 것을 막을
뿐, 실패 자체를 줄이지 않습니다.

날짜 하나를 펼치면 구글을 **최대 36번** 부릅니다. 그것도 줄줄이, **시간
제한 없이** — `RestClient.builder().baseUrl(...).build()` 에 연결·읽기
제한이 없습니다. 몰아치다 일부가 거절당하는 것일 수 있습니다.

로그가 가려 줍니다.

```bash
docker compose logs api | grep -E "경로가 비었습니다|경로를 받지 못했습니다" | tail -30
```

`받지 못했습니다` 가 섞여 있으면 시간 제한과 다시 묻기를 답니다.
`비었습니다` 만 있으면 §4 로 갑니다.

### 6.6 이번에 잰 것

`./gradlew test` 34 통과, icon 42 · trip 60 · place 9, 전부 0 실패.

## 7. 걸어서 14시간

세 번째로 들은 말입니다.

> 구글맵에서는 나리타공항에서 닛포리 역까지 대중교통 안내 해주는데 왜 우린
> 도보를 알려줘? **도보는 14시간인데** 이게 말이 된다고 생각하나?

말이 안 됩니다. 그리고 이건 **구글 사정이 아니라 우리 잘못**입니다.

### 7.1 걷기에 한계가 어디에도 없었습니다

구글이 대중교통을 안 줬고, 남은 것이 걷기와 차였습니다. 여기까지는 구글
사정입니다. 그런데 우리가 그 둘을 그대로 내놓았습니다.

**더 나쁜 것이 있었습니다.** `pick(cheapest)` 가 요금 없는 것을 **0원**으로
셉니다.

```java
long mine = o.fare() == null ? 0 : o.fare().amount();
```

걷기는 요금이 없습니다. 그래서 **14시간 걷기가 1시간 택시보다 "싸다"** 고
뽑혀서, 추천으로까지 올라갔습니다. 돈을 아끼자고 13시간을 더 쓰는 사람은
없습니다.

### 7.2 시간만 보고 자르지 않았습니다

두 시간 걷는 것이 답인 자리가 있습니다 — 산길이나 둘레길처럼 **걷는 것이 곧
목적**인 곳입니다. 길이만으로 자르면 그런 멀쩡한 답을 지웁니다.

그래서 **훨씬 나은 대안이 있을 때만** 뺍니다.

| | |
|---|---|
| 90분 아래 | **그대로 둡니다.** 5분 길을 30분 걷는 것은 사람이 실제로 고르는 선택입니다 |
| 90분 위 + 다른 수단이 **세 배 넘게** 빠름 | 뺍니다 |
| 걷는 것 말고 길이 없음 | **그대로 둡니다.** 그때는 그것이 유일한 답입니다 |

나리타는 14시간 대 1시간이라 빠집니다. 산길 네 시간은 대안이 없으면
남습니다.

### 7.3 잰 것

`SillyWalkTest` **7 통과 / 0 실패** (새로). 나리타 경우를 그대로 한 줄로
넣었습니다.

| 무엇을 | |
|---|---|
| **나리타에서 닛포리까지 걸어가라고 하지 않는가** | 14시간 vs 1시간 → 뺍니다 |
| 30분 걷기는 그대로 두는가 | 5분 차와 여섯 배 나도 둡니다 |
| 걷는 것 말고 길이 없으면 두는가 | 산길 네 시간 |
| 대안이 조금 빠른 정도면 두는가 | 두 시간 vs 한 시간 |
| **뺀 뒤에는 싼 쪽 추천도 걷기가 아닌가** | 진짜 고장이 여기였습니다 |

`./gradlew test` 41 통과(신규 7), icon 42 · trip 60 · place 9, 전부 0 실패.

### 7.4 남은 것

**대중교통이 왜 안 왔는지는 여전히 모릅니다.** 나리타~닛포리는 스카이라이너가
다니는 자리라 §4 의 "지역" 이나 "너무 가까움" 으로는 설명이 안 됩니다.

§2 를 올리고 나서도 안 나오면 §6.5 의 로그를 봐야 합니다. 그때 §2 가
들어가 있었는지부터 확인해야 합니다 — 안 들어가 있었으면 **새벽에 물어서
열차가 없다고 답한 것**일 수 있습니다.

## 8. 진짜 원인 — 소요시간을 못 읽고 있었습니다

§2 를 올리고도 나리타~닛포리에 대중교통이 안 나왔습니다. 그러면 §2·§4 의
짐작이 전부 틀린 것입니다.

코드를 다시 봤습니다.

```java
String digits = text.endsWith("s") ? text.substring(0, text.length() - 1) : text;
return Integer.parseInt(digits);     // "2460.000s" → 터집니다 → 0
```

**구글의 `Duration` 은 소수점이 붙어 옵니다.** 프로토버프 JSON 규칙이
그렇습니다 — *"0·3·6·9 자리의 소수"* 뒤에 `s` 를 붙입니다. 그래서
`"2460s"` 도 오고 `"2460.000s"` 도 옵니다.

`Integer.parseInt("2460.000")` 은 터집니다. 그러면 **0초**가 되고,
`compare` 가 이렇게 거릅니다.

```java
if (leg.reachable() && leg.seconds() > 0) {   // 0 이면 안 담습니다
```

**그 수단이 목록에서 통째로 사라집니다.**

### 8.1 그래서 로그에 아무것도 없었습니다

제가 §4·§6.5 에서 로그를 보라고 한 것이 헛다리였습니다. 이 경로는

- `경로가 비었습니다` 를 안 찍습니다 — **경로는 멀쩡히 왔습니다**
- `경로를 받지 못했습니다` 도 안 찍습니다 — **오류가 안 났습니다**

우리가 못 읽은 것뿐입니다. 그래서 **구글맵에는 나오는 대중교통이 우리
앱에서만 없었습니다.**

### 8.2 수단이 들쭉날쭉하던 것도 이것입니다

같은 구간이라도 구글이 어떨 때는 `"2460s"` 로, 어떨 때는 `"2460.000s"` 로
줍니다. 정수로 오면 보이고 소수로 오면 사라집니다. **자리마다 다른 수단이
빠지던 이유**입니다.

§6 의 캐시 고침이 이것을 더 고약하게 만들고 있었습니다 — 한 번 사라지면
여섯 시간을 갔으니까요.

### 8.3 고친 것

소수를 그대로 받아 반올림합니다. 초 아래는 이동 시간에서 뜻이 없습니다.
못 읽으면 로그를 남깁니다 — **조용히 0 을 돌려주는 것이 이 고장의 전부**
였습니다.

### 8.4 잰 것

`DurationParseTest` **5 통과 / 0 실패** (새로).

| 무엇을 | |
|---|---|
| **소수점이 붙어 와도 읽는가** | `2345.500s` → 2346초 |
| 정수로 와도 그대로 읽는가 | `2345s` → 2345초 |
| 못 읽는 것은 0인가 | `null` · 빈 값 · `한참s` |
| 음수는 0인가 | |
| **나리타~닛포리가 안 사라지는가** | `2460.000s` → 41분 |

옛 코드로 같은 값을 넣어 보면 이렇습니다.

```
2460s        → 2460초
2460.000s    → 0초   ★사라짐★
2345.500s    → 0초   ★사라짐★
```

### 8.5 이제 §4 는 어떻게 되나

§4 에 "지역" 과 "너무 가까움" 을 적어 뒀는데, **적어도 나리타 건은 둘 다
아니었습니다.** 남은 둘은 여전히 있을 수 있는 이유지만, 이번 증상의 원인은
아니었습니다.

§6.5 의 "시간 제한과 다시 묻기" 도 **아직 안 합니다.** 실패 로그가 실제로
나오는지부터 보고 정합니다 — 없는 병에 약 짓지 않습니다.

## 9. 가설이 셋 다 죽었습니다 (2026-09-14)

`962b5b5` 까지 올리고도 도쿄에서 대중교통이 하나도 안 나왔습니다. 서버
로그를 받았습니다.

```
경로가 비었습니다: mode=TRANSIT 35.770178,140.3843215 -> 35.7281578,139.7706414 응답={}
경로가 비었습니다: mode=TRANSIT 35.7281578,139.7706414 -> 35.6905894,139.7684302 응답={}
... (아홉 줄 전부 mode=TRANSIT, 전부 응답={})
```

### 9.1 로그가 지운 것

| 의심했던 것 | 로그가 말하는 것 |
|---|---|
| 대중교통을 **아예 안 묻는다** | 아닙니다. `mode=TRANSIT` 이 또박또박 나갑니다 |
| **오류**가 나서 빠진다 | 아닙니다. `경로를 받지 못했습니다` 가 한 줄도 없습니다. **200 에 빈 답**입니다 |
| **소수점 소요시간**(§8) | 아닙니다. 읽을 경로 자체가 안 왔습니다 |
| **거리**가 짧아서 | 아닙니다. **55.6km(나리타→닛포리)도, 도쿄 한복판 4.2km 도 똑같이 비었습니다** |

### 9.2 그리고 날짜도 아니었습니다

"그 날짜의 시각표가 아직 없는 것" 이라고 보고, 빈 답이 오면 지금 다니는
것으로 다시 묻는 코드를 넣었습니다. **되돌렸습니다** — 오늘 날짜로도,
일주일 뒤로도 똑같이 안 나온다고 합니다.

죽은 가설에 맞춘 코드를 남겨 두면 구글 호출만 두 배가 됩니다.

### 9.3 제가 계속 헛짚은 이유

**응답만 남기고 요청은 안 남겼습니다.**

빈 답이 왔을 때 "구글이 없다고 했다" 까지는 알아도, **우리가 정확히 뭘
물었는지**를 알 방법이 없었습니다. 도쿄 한복판 4km 에 전철이 없다고 나오면
의심해야 하는 것은 **답이 아니라 질문**입니다.

그래서 짐작을 네 번 했고 네 번 다 빗나갔습니다. 고친 것들은 전부 진짜
결함이었지만(§2·§6·§7·§8), **어느 것도 이 증상의 원인이 아니었습니다.**

### 9.4 이번에는 계측기를 답니다

빈 답이 왔을 때 **몸통을 함께 남깁니다.**

```
경로가 비었습니다: mode=TRANSIT 35.77,140.38 -> 35.72,139.77
  | 물은 것={origin=..., travelMode=TRANSIT, departureTime=..., ...}
  | 받은 것={}
```

키는 안 남습니다 — 몸통에 없습니다(헤더로 갑니다). 좌표는 이미 찍히고
있었고, 사람이 일정에 스스로 넣은 자리라 자취가 아닙니다.

**다음 로그 한 줄이면 끝납니다.** 우리가 보낸 `departureTime` 이 과거인지,
`travelMode` 가 제대로 실렸는지, 다른 무엇이 섞였는지가 거기 그대로
보입니다.

## 10. 답 — 구글이 일본에 대중교통을 안 줍니다

계측기를 달고 요청을 받았습니다.

```json
{
  "origin":      {"location":{"latLng":{"latitude":35.770178,"longitude":140.3843215}}},
  "destination": {"location":{"latLng":{"latitude":35.7281578,"longitude":139.7706414}}},
  "travelMode":  "TRANSIT",
  "languageCode":"ko",
  "units":       "METRIC",
  "departureTime":"2026-10-08T06:50:00Z"
}
```

### 10.1 요청은 완벽했습니다

| | |
|---|---|
| `travelMode` | `TRANSIT` — 제대로 실렸습니다 |
| 좌표 | 나리타공항 → 닛포리. 맞습니다 |
| `departureTime` | `06:50Z` = **일본 15:50**. 뒤 구간들도 16:30·18:00·18:30… 저녁 일정 그대로입니다 |
| 시간대 변환 | **맞습니다.** 경도 140도 → +9 |

**고칠 데가 없습니다.** 그런데 답은 `{}` 입니다.

### 10.2 그래서 찾아봤습니다

구글 개발자 포럼에 같은 글이 있습니다 — **일본에서 Directions/Routes API 의
대중교통만 결과가 안 나오고**, 응답의 `available_travel_modes` 에
`DRIVING`·`WALKING`·`BICYCLING` 만 들어 있고 `TRANSIT` 은 없습니다.

구글 문서도 이렇게 적어 두었습니다.

> 그 지역에 해당 길찾기가 없으면 `ZERO_RESULTS` 를 돌려줍니다. 나라별로
> 어떤 길찾기를 지원하는지는 **Coverage Details** 를 보십시오.

**구글 지도 앱에 나오는 것과 API 로 주는 것이 다릅니다.** 일본 철도 데이터는
소비자용 앱에는 들어가지만 API 로는 안 나옵니다.

### 10.3 우리 잘못이 아니었습니다 — 다만 하나 남습니다

앱은 제대로 묻고 있었습니다. 구글이 안 줄 뿐입니다.

**그런데 우리는 그것을 알고도 아무 말을 안 했습니다.** 대중교통을 조용히
지웠고, 그래서 쓰는 사람은 **앱이 고장 난 줄** 알았습니다 — 구글 지도에는
나오는 스카이라이너가 여기만 없으니까요.

**모르는 것을 아는 척하지 않는 것만큼, 아는 것을 말하지 않는 것도 틀린
일입니다.**

### 10.4 그래서 말해 줍니다

> 이 지역은 구글이 대중교통 길찾기를 내주지 않습니다. 구글 지도 앱에서는
> 보이지만 다른 앱으로는 가져올 수 없는 자리입니다.

**아무 때나 띄우지 않습니다.** 구간 하나가 비는 것은 흔합니다 — 몇백 미터에
전철이 없는 것은 맞는 답입니다. 그래서 **전철을 탈 만한 구간(2km 이상)이
있는데 그중 하나도 안 나왔을 때**만 말합니다.

판단은 서버가 합니다. 짧은 구간만 있는 하루를 "이 지역은 대중교통이 없다"
로 읽으면 안 되는데, 그 셈은 구간을 다 가진 쪽이 해야 맞습니다.
