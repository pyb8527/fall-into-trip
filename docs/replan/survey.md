# 밖에서는 무엇을 하고 있나 — 일정이 흐트러졌을 때

> 2026-09-14 에 **계획이 어긋난 뒤**를 다루는 기능만 따로 본 기록입니다.
> 판단은 `verdict.md` 에서 합니다. 여기서는 좋다·나쁘다를 쓰지 않습니다.
> 아직 코드는 한 줄도 바뀌지 않았습니다.

## 왜 이 축인가

앞선 조사가 이것을 남겨 두었습니다. `docs/during-trip/verdict.md` 의 "조사에
없었지만 눈에 띈 자리" 입니다.

> **여행 중에 일정이 흐트러지는 것을 다루는 곳이 없습니다.** 비가 오거나 줄이
> 길어서 하나를 건너뛰면, 그 뒤가 전부 밀립니다. 조사한 열셋 중 이것을 다루는
> 것이 없었습니다. 계획 앱은 짜는 것까지, 지도 앱은 한 구간까지입니다.

그리고 같은 문서가 **FIT 에는 붙을 자리가 이미 서 있다**고 적었습니다 —
`trip/domain/RouteTidy.java` 의 제안 → 비교 → 수락 → 되돌리기, 그리고
`CandidateService` 의 전원 동의. 둘 다 지금은 **계획 단계에만** 쓰입니다.

이번에는 그 빈자리를 직접 팠습니다. 앞선 두 조사와 겹치는 것은 뺐습니다 —
날씨 자체(`during-trip` 5번), 실시간 출발(4번), 항공편 상태·게이트(11번),
잠금화면 위젯(`2026-09` 14번)은 다시 조사하지 않았습니다. 여기서는 **그것이
일정을 어떻게 바꾸는가**만 봅니다.

## 어디를 봤나

| 갈래 | 본 것 | 조사일 |
|---|---|---|
| 경쟁 앱 | MonkeyTravel, Wanderlog, TripIt Pro, 트리플, Troupe, Limbo, AvoSquado, WePlanify | 2026-09-14 |
| 최근 1년 신기능 | MonkeyTravel 라이브 트립, TripIt Alternate Flights·Risk Alerts, 일본의 유료 줄서기(2026) | 2026-09-14 |
| 플랫폼 | Routes API `departureTime`·`arrivalTime`·`trafficModel` | 2026-09-14 |
| 불평·현장 | 일정 충돌 경고를 다루는 글, 일본 식당 대기 서비스, 한국어 커뮤니티 | 2026-09-14 |

### 출처 이해관계를 먼저 밝힙니다

**이번 조사에서 가장 결정적인 글이 경쟁 앱 자기네 블로그입니다.** 아래 1·2·12
번의 근거인 MonkeyTravel 의 "AI 트립 플래너 일곱을 견줘 봤다" 글은 그
앱을 파는 쪽이 썼습니다. 거기서 "다른 일곱은 여행 중 수정을 아무도 안 한다"
고 결론 내는데, **그 결론은 자기 앱만 한다는 말과 같습니다.** 기능 설명은
옮기되 그 비교 결론은 그대로 믿지 않습니다.

그룹 투표 앱들(10번)의 근거도 대부분 비교 listicle 이라 제휴 링크가 붙어
있을 수 있습니다.

### FIT 쪽 사실을 미리 넷 적어 둡니다

판단이 아니라 조사 중에 코드에서 확인한 것입니다. 2단계가 여기서 시작합니다.

- **`Place.time` 이 글자 칸입니다.** `trip/domain/Place.java:68` —
  `private String time`. "12:30" 도 "점심때쯤" 도 "오픈런" 도 들어갑니다.
  아래 3·4·5번이 전부 **시각을 숫자로 읽는 것**을 전제합니다.
- **`RouteTidy` 가 이미 다시 세웁니다.** 다만 **거리** 기준이고 시간 기준이
  아닙니다. 주석이 "시간을 적어 둔 곳은 움직이지 않습니다. 12:30 예약은
  12:30 입니다" 라고 적어, 시각이 있는 곳을 **기둥**으로 두고 나머지만 끼워
  넣습니다. 재는 것은 직선거리입니다 — "열 곳이면 아흔 번" 구글을 부르게 되기
  때문입니다.
- **`CandidateService` 에 `pour` 가 있습니다**(`:166`). 후보를 골라 **어느
  날에 붓는** 메서드입니다. `vote`(`:124`)·`listOf`·`add`·`remove` 와 함께
  계획 단계에 서 있습니다.
- **알림은 전날 저녁 여덟 시 한 번뿐입니다.** `TripReminder` 의
  `@Scheduled(cron = "0 0 20 * * *")`. 여행 중에 울리는 알림이 없습니다.

## 1. "늦었다" 한 번 누르면 남은 일정이 밀린다

**한 줄** — 단추 하나로 오늘 남은 것이 통째로 뒤로 밀립니다.

**어떻게 동작하나**
MonkeyTravel 의 라이브 트립 화면에 한 번 누르는 단추가 **넷** 있습니다.

| 단추 | 무엇이 일어나나 |
|---|---|
| 끝냄 | 그 일정을 다녀온 것으로 표시 |
| 건너뜀 | 안 가기로 하고 뺌 |
| **늦음** | **그날 남은 일정이 밀립니다** |
| 바꿈 | 근처의 다른 것으로 교체 (아래 2번) |

**무엇을 요구하나**

| 항목 | |
|---|---|
| 위치 | 불필요 |
| 사진·파일 | 불필요 |
| 푸시 | 불필요 |
| 외부 API | 불필요 (밀기 자체는 셈입니다) |
| 서버 저장 | 바뀐 시각 |

**출처** — <https://monkeytravel.app/blog/best-ai-trip-planners-2026-compared> (2026-09-14 확인 · **그 앱을 파는 쪽의 글**)

**규칙에 걸릴 수 있는 곳** — "사람이 수락해야 바뀝니다"
(`trip/domain/RouteTidy.java`). 단추를 누른 것이 수락인지, 밀린 결과를 보고
다시 수락해야 하는지가 갈립니다. 그리고 `Place.time` 이 글자라 **무엇을
얼마나 미는지** 가 지금 구조에서는 안 나옵니다.

**확인 못 한 것** — 얼마나 미는지(고정 15분인지, 실제 지연만큼인지), 되돌릴
수 있는지, 확인을 묻는지, 인터넷이 필요한지. **글 하나에서만 봤고 앱을 직접
써 보지 않았습니다.** 그 글은 파는 쪽 글입니다.

## 2. 근처의 다른 것으로 바꾸기

**한 줄** — 못 가게 된 자리를 근처의 대안으로 교체합니다.

**어떻게 동작하나**
위 넷 중 마지막입니다. 한 일정을 "근처 대안" 으로 바꿉니다. 무엇을 기준으로
고르는지는 글에 없습니다.

**무엇을 요구하나**

| 항목 | |
|---|---|
| 위치 | 필요할 가능성이 큼 ("근처") |
| 외부 API | 장소 검색 |
| 서버 저장 | 바뀐 장소 |
| 구글 호출 | 대안을 찾을 때마다 |

**출처** — 위와 같음 (2026-09-14 확인)

**FIT 쪽 사실** — 대안을 찾는 장치가 이미 있습니다. `RecommendService` 와
`components/recommend-sheet.tsx` 가 **지금 서 있는 자리 기준**으로 장소를
찾아 주고(`recommend-sheet.tsx:92` — "길 위에서 묻는 것은 대개 그 뜻입니다"),
그날 문을 여는지까지 봅니다. 없는 것은 **바꿔치기** 하나입니다.

**확인 못 한 것** — 고르는 기준(갈래가 같은 것인지, 평점인지, 거리인지).

## 3. 이동 시간을 보여 주어 무리한 일정을 미리 알기

**한 줄** — 구간마다 걸리는 시간과 하루 합계를 적어 둡니다.

**어떻게 동작하나**
Wanderlog 가 합니다. 하루에 장소를 끌어다 놓으면 **구간마다 예상 이동
시간**이 붙고, 하루 **총 시간과 총 거리**도 나옵니다. 다 들어가는지를 사람이
보고 판단하게 하는 방식입니다.

**"무리한 일정입니다" 라고 말해 주는 경고는 못 찾았습니다.** 도구는 주고
판단은 사람이 합니다.

**한계도 적혀 있습니다** — 이동 시간 추정이 늘 정확하지도, 늘 있지도
않습니다.

**무엇을 요구하나**

| 항목 | |
|---|---|
| 위치 | 불필요 |
| 외부 API | 경로 |
| 서버 저장 | 0 |
| 구글 호출 | 구간 수만큼 |

**출처**
- <https://help.wanderlog.com/hc/en-us/sections/5154228681883--Daily-itinerary> (2026-09-14 확인)
- <https://community.ricksteves.com/travel-forum/general-europe/trial-of-wanderlog-and-tripit-inspired-by-trip-research-post> (2026-09-14 확인)

**FIT 쪽 사실** — 구간 시간은 이미 있습니다. `RouteService.of(me, dayId, mode)`
가 하루치를 한 번에 계산하고 `DayRoute(mode, legs, totalSeconds, totalMeters, …)`
로 **합계까지** 돌려줍니다(`:438`). `DayExtrasController:32` 의
`GET /api/days/{dayId}/route` 입니다. 없는 것은 **그 합계를 하루 길이와
견주는 것**입니다.

**확인 못 한 것** — Wanderlog 가 "하루 몇 시간" 을 어디서 얻는지(사람이 적은
시각인지, 정해 둔 활동 시간인지).

## 4. 시각이 겹치면 빨간 테두리

**한 줄** — 두 일정이 같은 시각을 쓰면 그 자리에서 말해 줍니다.

**어떻게 동작하나**
일정·회의 도구 쪽의 흔한 모양입니다. 겹치는 것 **양쪽에 빨간 테두리**가
생기고, 화면 위에 "N개 충돌" 띠가 뜹니다. 일정을 넣는 **그 순간** 갱신되고
고치면 바로 사라집니다.

여행 쪽에도 같은 것을 만든 사례가 있습니다. 한 여행 플래너의 이슈에
`date clash prevention` 이 적혀 있습니다 — 겹치는 구간과 뒤집힌 날짜 범위를
잡아내고, **충돌이 있으면 저장 단추를 잠그고** 설명 띠를 띄웁니다.

**무엇을 요구하나**

| 항목 | |
|---|---|
| 위치 | 불필요 |
| 외부 API | 불필요 |
| 서버 저장 | 0 — 화면에서 셈합니다 |
| 전제 | **시각을 숫자로 읽을 수 있어야 합니다** |

**출처**
- <https://github.com/Trentan/travel-planner/issues/213> (2026-09-14 확인)
- <https://agendaforge.app/tools/schedule-conflict-checker> (2026-09-14 확인)

**규칙에 걸릴 수 있는 곳** — "사람이 자유롭게 적은 칸을 숫자로 읽지
않습니다"(`references/house-rules.md`). `Place.time` 이 글자 칸이라
(`Place.java:68`) "점심때쯤" 같은 것이 들어 있습니다. 저장을 잠그는 쪽은 특히
걸립니다 — 못 읽은 것을 충돌로 보면 멀쩡한 일정이 안 저장됩니다.

**확인 못 한 것** — 여행 앱 중에 이것을 실제로 내놓은 곳. 찾은 것은 오픈소스
이슈 하나와 일반 일정 도구들입니다.

## 5. 하나가 밀리면 뒤가 따라 밀림 (cascade)

**한 줄** — 앞 일정을 하루 미루면 뒤도 함께 움직입니다.

**어떻게 동작하나**
위와 같은 여행 플래너 이슈에 `dynamic day increment / cascade` 로 적혀
있습니다. **켜 두면** 뒤 날짜들이 자동으로 따라 밀리고, 여행의 날·이동·숙박이
서로 어긋나지 않게 유지됩니다.

핵심은 **켜고 끌 수 있다**는 것입니다. 늘 따라 미는 것이 아닙니다.

**무엇을 요구하나**

| 항목 | |
|---|---|
| 위치 | 불필요 |
| 외부 API | 불필요 |
| 서버 저장 | 바뀐 날짜들 |
| 전제 | 무엇이 무엇에 매여 있는지 알아야 합니다 |

**출처** — <https://github.com/Trentan/travel-planner/issues/213> (2026-09-14 확인)

**규칙에 걸릴 수 있는 곳** — "사람이 수락해야 바뀝니다". 하나를 고쳤는데 열이
움직이는 것은 이 규칙이 가장 조심하는 모양입니다.

**확인 못 한 것** — 되돌리기가 있는지. 이슈 제목만 봤고 구현을 못 봤습니다.

**어떻게 동작하나**
TripIt Pro 의 Alternate Flights 입니다.

**출처**

## 7. 어긋나기 전에 미리 알려 주기 (Risk Alerts)

**한 줄** — 공항이나 항공사에 무슨 일이 생기면 내 여행에 닿기 전에 알립니다.

**어떻게 동작하나**
TripIt Pro 의 Risk Alerts 입니다. 내 일정에 **영향을 줄 수 있는** 항공사·공항
사건이 생기면 알림이 옵니다. 지연이 확정된 뒤가 아니라 **그 전**에 알리는
것이 요지입니다.

같은 묶음으로 EU 구간 지연·결항 보상을 AirHelp 과 연결해 주는 것도
있습니다 — 지난 3년치까지 봅니다.

**무엇을 요구하나**

| 항목 | |
|---|---|
| 위치 | 불필요 |
| 푸시 | **필요** |
| 외부 API | 운항·사건 데이터 |
| 계정 연동 | 보상 쪽은 AirHelp 연동 |
| 서버 저장 | 일정과 편명 |

**출처** — <https://www.tripit.com/web/blog/news-culture/tripit-pro-risk-alerts> · <https://www.tripit.com/web/blog/travel-tips/flight-disruptions-tripit-partner-airhelp> (둘 다 2026-09-14 확인)

**규칙에 걸릴 수 있는 곳** — 보상 연동은 **돈이 오가는 자리**를 새로 만드는
일입니다. "돈은 껄끄러움을 없애는 자리" 규칙과 방향을 봐야 합니다.

**확인 못 한 것** — 한국 출발·도착 노선에 이 알림이 실제로 오는지.

## 11. 출발·도착 시각을 넣어 길을 묻기

**한 줄** — "지금 출발하면" 이 아니라 "3시에 출발하면" 을 물을 수 있습니다.

**어떻게 동작하나**
Routes API 의 `computeRoutes` 가 `departureTime` 과 `arrivalTime` 을 받습니다.

| | |
|---|---|
| 대중교통 | 둘 중 **하나만** 줍니다. 둘 다는 안 됩니다 |
| 대중교통 기간 | **과거 7일 ~ 미래 100일** |
| 자동차 | `departureTime` 은 되지만 **과거는 안 됩니다**(과거는 대중교통만) |
| `arrivalTime` | 대중교통이 아니면 **무시됩니다** |
| 교통 상황 | `trafficModel` 은 `RoutingPreference` 가 `TRAFFIC_AWARE`·`TRAFFIC_AWARE_OPTIMAL` 이고 자동차일 때만. 기본값 `BEST_GUESS` |

| 항목 | |
|---|---|
| 위치 | 불필요 |
| 외부 API | 이미 쓰는 Routes |
| 서버 저장 | 0 |

**출처** — <https://developers.google.com/maps/documentation/routes/reference/rest/v2/TopLevel/computeRoutes> (2026-09-14 확인)

## 눈에 띈 것

**여럿이 공통으로 가진 것**

- **도구는 주고 판단은 사람이 합니다.** Wanderlog 는 이동 시간을 보여 주되
  "무리입니다" 라고 말하지 않습니다. TripIt 은 대체편을 찾아 주되 예약은
  안 합니다. **앱이 대신 정해 주는 자리는 거의 없습니다.**
- **떠나기 전에 몰려 있습니다.** 그룹 투표 앱 넷 중 여행 중 재합의를
  내세우는 곳이 없었습니다. Troupe 는 "정하고 나면 할 일이 끝난다" 고 스스로
  적습니다.
- **유료 벽.** 어긋난 뒤를 다루는 기능은 대개 유료입니다 — Alternate
  Flights·Risk Alerts 는 TripIt Pro, 줄 서기는 건당 결제입니다.

**아무도 안 하는 것 — 이번에도 남았습니다**

- **밀린 결과를 견줘 보여 주고 수락받는 것.** "늦음" 을 누르면 밀린다는
  앱은 찾았지만, **밀기 전과 후를 나란히 보여 주고 고르게 하는 것**은 못
  찾았습니다. FIT 의 `RouteTidy` 가 거리에 대해 이미 그 모양을 하고 있습니다 —
  `Tidied(order, beforeMeters, afterMeters)` 로 전후를 함께 돌려주고
  `worthIt()` 으로 "몇 미터 차이로 바꾸자고 물으면 성가십니다" 를 거릅니다.
- **밀린 뒤에 문을 닫는지 다시 보는 것.** 9번의 권고가 그것을 말하는데
  (영업시간·입장권·예약을 다시 확인하라), 자동으로 해 주는 곳은 못 봤습니다.
  FIT 은 `PlaceInfoService` 가 **그날** 영업 여부를 이미 봅니다.

**이번 조사에서 가장 걸리는 것**

**`Place.time` 이 글자 칸이라는 것**입니다(`Place.java:68`). 3·4·5번이 전부
시각을 숫자로 읽는 것을 전제하는데, 이 앱은 일부러 자유롭게 적게 두었습니다.
그리고 `house-rules` 에 **"사람이 자유롭게 적은 칸을 숫자로 읽지 않습니다"**
가 있습니다. 2단계에서 이것을 먼저 정해야 나머지가 정해집니다.

**조사에서 못 채운 자리**

- **가장 중요한 앱을 파는 쪽 글로만 봤습니다.** 1·2·12번의 근거가
  MonkeyTravel 자기네 비교 글 하나입니다. 앱을 직접 안 써 봤고, "다른 일곱은
  아무도 안 한다" 는 결론은 그대로 옮기지 않았습니다.
- **레딧을 또 못 봤습니다.** 크롤러가 막혀 있습니다. 불평 축이 이번에도
  약합니다 — "일정이 밀려서 불편하다" 는 **제가 앞선 조사에서 관찰로 적은
  것**이지, 사용자 글로 확인한 것이 아닙니다.
- **Routes API 요금 등급표를 세 번째로 못 봤습니다.** 11번의 값을 못 셉니다.
- **숫자는 출처가 있는 것만 적었습니다.** 일본 줄서기 서비스의 가맹 수와
  이용자 연령대는 기사에 있는 값이고, 나머지는 안 적었습니다.
