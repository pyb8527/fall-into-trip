# 붙여 넣은 예약 확인서를 그 자리에서 칸으로 — 기기 안에서

> `verdict.md` 2번에서 **재설계 권장**으로 받은 것의 실행 계획입니다.
> 아직 코드는 한 줄도 바뀌지 않았습니다.
>
> 이 폴더의 계획은 하나씩 따로 씁니다. 그래서 `plan.md` 가 아니라
> `plan-booking-paste.md` 입니다. 다음 계획도 `plan-<무엇>.md` 로 씁니다.

## 1. 하려는 것

지금은 사람이 **옮겨 적습니다.**

`StaySheet`(`frontend/src/app/trip/[id].tsx:2666`)에 칸이 셋 있습니다 —
잘 곳, 메모, 그날 타는 편. 자리표시 글자가 그 칸들이 무엇을 기다리는지
말해 줍니다.

```
메모          체크인 15시 · 305호
그날 타는 편   OZ112 09:20 인천 T1 → 간사이
```

그 글자는 **예약 확인 메일에 이미 다 적혀 있습니다.** 사람이 지금 하는 일은
메일 앱을 열고, 편명을 외우고, FIT 으로 돌아와 적고, 시각이 맞는지 다시
확인하러 메일 앱으로 돌아가는 것입니다. 칸이 셋이니 그 왕복이 셋입니다.

TripIt 이 2026년에 Pro 전용으로 내놓은 것이 이 왕복을 없애는 일이고, 핵심은
**기기 안에서 글자를 뽑는다**는 것입니다. 우리는 그 장치를 이미 갖고 있습니다.

## 2. 이미 있는 것

새로 만들 것이 거의 없습니다. 그래서 이 계획이 1차에 있습니다.

| 필요한 일 | 지금 어디에 있나 |
|---|---|
| 앱의 기기 안 모델 | `lib/intent.ts` — `react-native-executorch`, Qwen 2.5 1.5B 4비트. 세션을 모듈 안에 들고 재사용합니다(`:54`) |
| 웹의 기기 안 모델 | `lib/intent.web.ts` — 크롬 내장 모델 또는 WebLLM. 무거운 것은 눌렀을 때만 동적으로 불러옵니다 |
| 답 모양 강제 | `intent.web.ts` — `responseConstraint`(내장) · `response_format`(WebLLM) |
| 깨진 JSON 수습 | `intent-prompt.ts:70` `readIntent` — 중괄호 안쪽만 발라냅니다. 앱 쪽에 모양 강제가 없어서 필요합니다 |
| "null"·"없음" 걸러내기 | `intent-prompt.ts:111` `text()` |
| 모델 상태·받기 UI 관습 | `components/recommend-sheet.tsx:161-180` (`intentState`·`fetchModel`·`parseIntent`), `:345` ("이 기기 밖으로 나가지 않습니다") |
| 저장 API | `PATCH /api/days/{id}` → `DayService.DayPatch`(`:166-170`) |
| 넣을 칸 | `Day.flight`(`:56`), `Day.stayName`·`stayNote`(`:68-81`) |
| 권한 | `DayService.update:62-63` — `access.requireCanEdit` + `Versioned.check` |
| 붙일 화면 | `StaySheet`(`app/trip/[id].tsx:2666-2760`) |

**모델을 새로 받지 않습니다.** 추천을 쓰는 사람은 이미 받아 두었고, 같은
세션에 다른 프롬프트를 물립니다.

## 3. 버리는 것

### 3.1 사진과 PDF 읽기 — 버립니다

TripIt 이 하는 것은 사진·PDF 입니다. 우리는 **글자만** 받습니다.

OCR 엔진은 새 네이티브 의존이고 EAS 재빌드가 붙습니다. 그 순간 이 계획은
1차에서 2차로 내려가고, 웹에서는 또 다른 길이 필요해집니다. 붙여 넣기로
얻는 것이 그 값을 치를 만큼 적지 않습니다 — 예약 확인은 대개 메일이나
문자로 오고, 둘 다 글자를 복사할 수 있습니다.

Apple Intelligence 쪽은 애초에 못 씁니다. **iOS 전용**이고, 이 저장소의
실제 서비스는 nginx 가 내보내는 웹 빌드입니다.

### 3.2 자동 저장 — 버립니다

뽑아낸 값을 바로 저장하지 않습니다. 칸에 **채워 놓고 멈춥니다.** 사람이
보고, 고칠 것을 고치고, 지금처럼 "저장" 을 누릅니다.

`RouteTidy` 가 세워 둔 순서(제안 → 비교 → 수락 → 되돌리기)가 여기도
걸립니다. 그리고 실질적인 이유가 더 큽니다 — 모델이 날짜를 하루 틀리면
멀쩡한 일정이 하루 밀리고, 사람은 자기가 안 한 변경을 찾아내야 합니다.

### 3.3 좌표 짐작 — 버립니다

"호텔 그란비아 오사카" 라는 글자에서 위도·경도를 짐작하지 않습니다.
`stayLat`·`stayLng`·`stayPlaceId` 는 **비워 둡니다.**

그 일을 하는 것이 이미 있습니다 — `PlaceSearch` 가 같은 시트 안에 있고,
`StaySheet` 주석(`:2662-2668`)이 좌표를 받는 이유를 적어 두었습니다("이름만
으로는 숙소 근처 아침 먹을 데를 찾을 수 없고"). 모델이 짐작한 좌표를 넣으면
그 주석이 기대하는 것과 다른 것이 들어갑니다.

사람이 이름을 보고 `PlaceSearch` 로 한 번 고르면 좌표가 정확히 잡힙니다.
우리가 줄이려는 왕복은 메일 앱과의 왕복이고, 이건 시트 안에서 끝나는 일입니다.

### 3.4 날짜를 읽어 다른 날로 옮기기 — 버립니다

예약 확인서에는 날짜가 있습니다. 그 날짜로 **다른 `Day` 를 찾아가지
않습니다.**

`StaySheet` 는 이미 특정 날에서 열립니다(제목이 `${day.date || day.label} 잘 곳`).
사람이 그 날을 골라서 들어온 것이고, 앱이 그 선택을 뒤집을 이유가 없습니다.

다만 **읽은 날짜가 이 날과 다르면 말해 줍니다.** 조용히 채우면 사람은
3월 4일 예약을 3월 5일에 붙여 놓고 모릅니다.

### 3.5 원문을 서버로 보내기 — 버립니다

붙여 넣은 글에는 이름·예약번호·카드 뒷자리·전화번호가 들어 있습니다.
**쪼개는 일은 기기에서 끝냅니다.** 서버로 가는 것은 사람이 수락한 칸 값
뿐이고, 그것은 지금 `PATCH /api/days/{id}` 가 받는 것과 똑같습니다.

그래서 **모델이 없는 기기에서는 이 단추를 아예 안 보여 줍니다.** 추천과
다릅니다 — 추천은 모델이 없으면 문장을 서버로 보내 맥락 검색으로
미끄러지지만, 여기서 미끄러지면 예약 확인서가 서버로 갑니다. 미끄러질
자리를 만들지 않는 것이 이 계획에서 가장 중요한 한 줄입니다.

## 4. 갈 곳

```
[사람]  예약 확인 메일에서 글자를 복사
          |
          v
  StaySheet 의 "예약 확인서 붙여 넣기" 칸
          |
          | canParseHere && intentState() === 'ready' 일 때만 보입니다
          v
  parseBooking(text)                    ← 기기 안. 밖으로 안 나갑니다
          |
          |  lib/intent.ts       (앱: ExecuTorch, 모양 강제 없음)
          |  lib/intent.web.ts   (웹: 내장 모델 또는 WebLLM, 모양 강제 있음)
          |         둘 다 lib/booking-prompt.ts 의 PROMPT·SCHEMA·readBooking 을 씁니다
          v
  Booking { kind, stayName, stayNote, flight, iso }
          |
          +-- null 이면 → "읽지 못했습니다" 한 줄. 칸은 그대로 둡니다
          |
          +-- iso 가 이 날과 다르면 → "3월 4일 예약으로 읽혔습니다" 를 함께 띄웁니다
          |
          v
  setNote() · setFlight() 로 칸을 채웁니다   ← 저장하지 않습니다
          |
          v
  [사람]  보고 고치고 "저장" 을 누릅니다
          |
          v
  PATCH /api/days/{id}   (지금 그대로. 서버는 한 줄도 안 바뀝니다)
```

## 5. 닿는 파일

| 파일 | 무엇을 |
|---|---|
| `frontend/src/lib/booking-prompt.ts` | **새로 만듭니다.** `PROMPT`·`SHOTS`·`BOOKING_SCHEMA`·`readBooking`. `intent-prompt.ts` 와 나란히 둡니다 |
| `frontend/src/lib/intent-types.ts` | `Booking` 타입을 더합니다 |
| `frontend/src/lib/intent.ts` | `parseBooking(text)` 를 더합니다. 세션(`:54`)과 `MAX_TOKENS` 를 그대로 씁니다 — 다만 뽑을 것이 많아 토큰을 늘려야 합니다 |
| `frontend/src/lib/intent.web.ts` | 같은 것을 더합니다. 모양 강제에 `BOOKING_SCHEMA` 를 넘깁니다 |
| `frontend/src/app/trip/[id].tsx` | `StaySheet`(`:2666`)에 붙여 넣는 칸과 "읽기" 단추. `PlaceSearch` **위**에 둡니다 |

**안 고치는 것** — 백엔드 전부, `api/` 전부, `recommend-sheet.tsx`,
`intent-prompt.ts`. 추천 쪽 프롬프트를 건드리지 않습니다. 한 파일에 두
프롬프트를 넣으면 한쪽을 고칠 때 다른 쪽이 조용히 달라집니다.

## 8. 순서와 의존

1. **`lib/booking-prompt.ts`** — 프롬프트·스키마·`readBooking`. 먼저 섭니다.
   나머지 둘이 이것을 가져다 씁니다.
2. **`lib/intent-types.ts`** 에 `Booking` — 1번과 함께.
3. **`lib/intent.web.ts` 의 `parseBooking`** — 웹부터 합니다. 모양 강제가
   있어서 프롬프트가 맞는지 먼저 확인하기 쉽고, 모델을 안 받아도 크롬
   내장으로 볼 수 있습니다.
4. **`lib/intent.ts` 의 `parseBooking`** — 앱. 모양 강제가 없어서
   `readBooking` 이 실제로 견디는지가 여기서 드러납니다.
5. **`StaySheet` 의 칸과 단추** — 마지막. 셋이 선 다음에 붙입니다.

3번과 4번은 서로 의존하지 않지만 **둘을 반쯤 해 놓지 않습니다.** 한쪽을
끝내고 다음으로 갑니다.

## 9. 아직 모르는 것

- **`MAX_TOKENS` 를 얼마로 둘지.** 지금 96 입니다(`intent.ts:44`). 추천은
  짧은 JSON 한 줄이지만 예약은 칸이 다섯입니다. 늘려야 하는데, 크게 잡으면
  모델이 말을 덧붙이기 시작할 때 그만큼 기다립니다. 실제로 넣어 보고 정합니다.
- **1.5B 가 이 일을 해내는지.** 문장을 세 칸으로 쪼개는 것과 예약 확인서에서
  다섯 칸을 뽑는 것은 난이도가 다릅니다. 편명·시각은 글자가 뚜렷해서 쉬울
  것 같고, 숙소 이름과 체크인 시각은 덜 그렇습니다. **못 해내면 이 계획을
  접습니다** — 서버로 보내는 길을 만들어서 메우지 않습니다(3.5).
- **`SHOTS` 를 몇 개 둘지.** 추천은 둘입니다(`intent-prompt.ts:34-39`, "둘이면
  충분하고 더 붙이면 매번 다시 읽어야 해서 느려집니다"). 예약은 갈래가
  둘(항공·숙소)이라 각 하나씩 둘이 필요할 수 있고, 그러면 넷입니다.
- **항공과 숙소를 한 번에 읽을지.** 예약 확인 메일은 대개 하나만 담고
  있지만, 패키지는 둘을 같이 담습니다. `kind` 를 하나로 둘지 둘 다 채울 수
  있게 할지 실제 메일을 보고 정합니다.
- **프런트 테스트 틀.** `readBooking`·`readIntent` 같은 순수 함수가 늘고
  있는데 확인할 자리가 없습니다. 이 계획 밖의 결정입니다.
- **앱이 실제로 쓰이는 비중.** 4번(앱 쪽 `parseBooking`)에 얼마나 공을 들일지가
  여기에 달렸습니다. README 는 실제 서비스가 웹 빌드라고 적습니다.
