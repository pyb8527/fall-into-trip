## 1. 하려는 것

지금은 갈 곳의 **이름을 알아야** 넣을 수 있습니다. `장소 찾기` 칸에
"난바 파크스" 를 적으면 좌표가 잡히지만, "오사카에서 비 올 때 갈 만한
실내" 는 적을 데가 없습니다. 그것은 사람이 블로그를 뒤져 이름을 알아낸
다음에야 FIT 으로 돌아오는 일이라, 정작 계획을 세우는 시간의 대부분이
앱 밖에서 흐릅니다.

말로 물으면 후보가 나오고, 그중 마음에 드는 것을 바로 일정이나 보석함에
담는 데까지가 목표입니다.

## 2. 이미 있는 것

원안이 STEP 4·5 로 적어 둔 일은 FIT 에서 이미 돌아갑니다. 새로 만들 것과
고쳐 쓸 것을 가르기 위해 먼저 적습니다.

| 원안의 단계 | FIT 의 현재 위치 |
|---|---|
| Places 호출 · 응답 정형화 | `PlaceSearchService` — Text Search, `Found(name, address, lat, lng, placeId, icon)` |
| 평점 · 영업시간 · 휴업 | `PlaceInfoService` — 브레이크 타임과 그 **날짜 기준** 개점 여부까지. 원안의 필드셋보다 넓습니다 |
| 카테고리 추론 | `PlaceKind.guess(types, name)` — 열여섯 갈래 |
| 결과 없음 | `PlaceSearchService` 의 `ZERO_RESULTS` 분기 |
| 호출 실패 | `BAD_GATEWAY` + "좌표를 직접 넣어 주세요" |
| 담아 두기 | `SavedPlaceService`(보석함) · `CandidateService`(후보·투표) |

**추천의 뒷부분은 이미 다 있습니다.** 없는 것은 앞부분 하나 — 사람의 말을
검색 인자로 바꾸는 일입니다.

## 3. 원안에서 버리는 것

원안을 그대로 옮기면 지금 서 있는 규칙 몇 개가 무너집니다. 무엇을 왜
버리는지 적어 둡니다. 나중에 "왜 명세서대로 안 했나" 를 다시 묻지 않기
위해서입니다.

### 3.1 앱에 API 키를 넣는 것 — 버립니다

원안은 앱이 `X-Goog-Api-Key` 를 붙여 구글을 직접 부릅니다. FIT 은 반대로
서 있고, 그 이유가 `PlaceSearchService` 주석에 이미 적혀 있습니다.

- 번들에 심은 키는 누구나 꺼내 씁니다. 우리 사용량을 남이 태웁니다.
- 브라우저에서 부르면 CORS 로 막힙니다.
- 웹과 앱이 다른 길을 쓰면 결과 모양이 갈리고 고칠 곳이 두 군데가 됩니다.

`application.yml` 도 이미 키를 둘로 갈라 둡니다 — 서버가 쓰는
`GOOGLE_MAPS_KEY`(IP 로 묶음)와 웹 지도가 쓰는
`EXPO_PUBLIC_GMAPS_KEY`(리퍼러로 묶음). **구글로 나가는 문은 서버 한 곳으로
유지합니다.** 온디바이스 모델을 넣더라도 이 규칙은 그대로입니다. 모델은
기기에서 돌지만, 그 모델이 만든 검색 인자는 우리 서버를 거쳐 구글로 갑니다.

### 3.2 오프라인 로컬 관광지 DB — 버립니다

원안 §8-1 은 SQLite/Room 에 기본 관광지를 심어 두라고 합니다. FIT 은
로그인과 동기화를 전제로 한 앱이라, 오프라인이면 애초에 일정도 못 봅니다.
장소 DB 만 따로 심으면 갱신 책임만 늘고 쓰이지 않습니다. 오프라인에서는
지금처럼 "지금은 찾을 수 없습니다" 로 정직하게 말합니다.

### 3.3 "인퍼런스 150ms" — 믿지 않습니다

원안은 1차 추론을 150ms 로 적었습니다. 게다가 추론이 **두 번**입니다(툴콜
JSON + 답변 합성). 중급 안드로이드에서 INT4 1.5B 모델의 첫 토큰까지는
그보다 한참 걸리고, 두 번이면 지금의 서버 왕복 한 번보다 느려질 수
있습니다. 3단계에서 실측하기 전까지 온디바이스를 "빠른 길" 로 부르지
않습니다. 온디바이스의 값어치는 속도가 아니라 **질의문이 서버로 나가지
않는다는 것** 에 둡니다.

## 5. 0단계 — Places API (New) 로 옮깁니다

추천과 무관하게 따로 값이 있는 일이라 먼저 합니다.

지금 부르는 `/maps/api/place/textsearch/json` 과 `/maps/api/place/details/json`
은 레거시입니다. 새 기능이 붙지 않고, 구글은 신규 프로젝트에서 이미 막고
있습니다. 원안 §5.3 이 쓰는 `places:searchText` 로 옮깁니다.

**바뀌는 곳**

- `PlaceSearchService.search()` — `POST /v1/places:searchText`,
  본문에 `textQuery`·`languageCode`, 헤더에 `X-Goog-Api-Key`·`X-Goog-FieldMask`
- `PlaceInfoService.ask()` — `GET /v1/places/{placeId}`, 같은 방식의 필드마스크
- 응답 파싱 — `results[]` 가 `places[]` 로, `name` 이 `displayName.text` 로,
  `geometry.location` 이 `location` 으로, `formatted_address` 가
  `formattedAddress` 로. 영업시간은 `"1130"` 문자열 대신
  `regularOpeningHours.periods[].open{hour, minute}` 숫자 쌍으로 옵니다 —
  `clock()` 이 하던 잘라 붙이기가 없어지고 자리맞춤 형식으로 바뀝니다.
- 상태 코드 — 새 API 는 `status: "OK"` 를 안 보내고 HTTP 코드로 말합니다.
  결과 없음은 **빈 `places` 배열** 이므로 `ZERO_RESULTS` 분기를 그렇게 고칩니다.

**바뀌지 않는 곳**

`Found` 와 `Info` 레코드의 모양, `PlaceController` 의 경로, 화면 전부.
계약을 그대로 두는 것이 이 단계의 핵심입니다.

**필드마스크** — 넓게 적으면 더 비싼 등급으로 넘어갑니다. 지금 화면이
실제로 쓰는 것만 적습니다.

```
검색:  places.id, places.displayName, places.formattedAddress,
       places.location, places.types
상세:  regularOpeningHours, utcOffsetMinutes, nationalPhoneNumber,
       websiteUri, rating, userRatingCount, businessStatus, googleMapsUri
```

사진과 후기는 여전히 받지 않습니다. 그쪽은 글쓴이 이름과 프로필을 함께
띄워야 하는 별도의 의무가 붙습니다 — `PlaceInfoService` 주석의 판단을
그대로 잇습니다.

**끝났다고 말할 수 있는 조건**
`backend/src/test/http/` 의 기존 검색·아이콘 테스트가 그대로 통과하고,
좌표·아이콘·영업시간이 이전과 같은 값으로 나옵니다.

## 6. 1단계 — 여행 맥락을 붙인 추천

**모델 없이** 원안이 노리던 것의 대부분을 얻는 단계입니다. Text Search 는
"오사카 비 올 때 갈 만한 실내" 같은 문장을 이미 상당히 잘 먹습니다. 우리가
보태야 할 것은 모델이 아니라 **맥락** 입니다 — 구글은 이 사람이 지금 어느
여행의 며칠째를 짜는 중인지 모릅니다.

### 6.1 새 길

```
POST /api/trips/{tripId}/recommend
{
  "query":  "비 올 때 갈 만한 실내",
  "dayId":  "…",                     // 없어도 됩니다. 있으면 그 날짜로 영업 여부를 봅니다.
  "here":   { "lat": 34.6, "lng": 135.5 }   // 없어도 됩니다.
}
```

`here` 를 쿼리스트링이 아니라 **본문**으로 받습니다. `PlaceController.fromHere`
가 이미 같은 이유로 그렇게 하고 있습니다 — 사람이 지금 어디 있는지는 nginx
접근 기록과 브라우저 방문 기록에 남길 값이 아닙니다.

응답은 `Found` 에 추천에만 필요한 것을 덧댄 카드입니다.

```json
{
  "places": [
    {
      "name": "…", "address": "…", "lat": 34.6, "lng": 135.5,
      "placeId": "…", "icon": "art",
      "rating": 4.4, "ratingCount": 4810,
      "openOnDay": true,
      "distanceM": 1200,
      "already": "candidate"
    }
  ],
  "source": "google",
  "note": null
}
```

`already` 는 이미 일정·후보·보석함에 있는 곳이라는 표시입니다. 없으면
같은 곳을 또 담게 되고, 서버가 조용히 무시하면 눌러도 아무 일도 안 일어난
것처럼 보입니다. `PlaceSearch` 의 `kept` 가 이미 같은 문제를 화면 쪽에서만
얕게 풀고 있는데, 여기서는 서버가 압니다.

### 6.2 맥락을 어디서 얻는가

- **어느 동네인가** — `Place` 들의 좌표 중심. 여행에 아직 아무것도 없으면
  `TripLocation`(지금 위치), 그것도 없으면 지역 편향 없이 검색합니다.
  `Trip` 에는 지역 칸이 없습니다. **새로 만들지 않습니다** — 일정에 꽂힌
  핀이 이미 그 답이고, 사람이 한 번 더 적게 하는 것은 손해입니다.
- **언제인가** — `dayId` 로 `Day.iso` 를 얻습니다. 그 날짜의 요일로 영업
  여부를 봅니다. `PlaceInfoService.viewOf` 가 이미 "오늘" 이 아니라 "그날"
  로 보고 있어서 그 판단을 그대로 씁니다.
- **이미 있는 것** — `PlaceRepository`·`TripCandidateRepository`·
  `SavedPlaceRepository` 에서 `placeId` 만 모아 대조합니다.

### 6.3 화면

`components/recommend-sheet.tsx` 하나. `PlaceSearch` 와 나란히 두되 섞지
않습니다. 이름으로 찾는 것과 말로 묻는 것은 기대하는 답이 다릅니다 —
전자는 "그것" 을 원하고 후자는 "그런 것들" 을 원합니다. 한 칸에 합치면
"난바 파크스" 를 넣었을 때도 추천 여섯 개가 나와 방해가 됩니다.

카드마다 단추 셋 — **일정에 넣기 · 후보로 올리기 · 보석함에 담기**.
후보로 올리는 길이 특히 중요합니다. 추천은 본래 확정이 아니라 의견이고,
`CandidateService` 가 그 의견을 동행자 전원의 합의로 바꾸는 자리를 이미
갖고 있습니다.

**끝났다고 말할 수 있는 조건**
웹과 안드로이드 앱에서 같은 질의가 같은 순서의 카드를 내고, 그중 하나를
후보로 올리면 `vote` 화면에 그대로 뜹니다.

## 7. 2단계 — 모델을 서버 뒤에 둡니다

1단계로 안 되는 것이 남습니다. "아이랑 가기 좋은" 같은 조건은 Text Search
가 문장 그대로는 잘 못 먹고, 여러 조건이 섞인 문장("첫날 저녁에 셋이서
조용히 술 한잔")은 검색어 하나로 눌러 담기 어렵습니다. 여기서 모델이
할 일은 **답을 짓는 것이 아니라 문장을 인자로 쪼개는 것** 입니다.

### 7.0 "서버 뒤" 는 자체 설치가 아닙니다

**모델을 우리 서버에 설치한다는 뜻이 아닙니다.** 호출이 서버를 거친다는
뜻입니다 — 앱은 우리 API 만 부르고, 밖으로 나가는 문은 3.1 대로 서버 한
곳입니다. 모델이 실제로 어디서 도는지는 그 뒤의 문제이고, 갈래는 둘입니다.

| | 외부 API 호출 (권장) | 자체 설치 |
|---|---|---|
| 모델이 도는 곳 | 사업자 서버 | 우리 서버 |
| 우리가 하는 일 | 키를 들고 대신 호출 | 추론 서버를 띄우고 운영 |
| 질의문 | 사업자에게 나감 | 안 나감 |
| 지금 서버 | 부담 없음 | GPU 가 없으면 CPU 추론 — db·api 와 RAM 을 다툽니다 |

**외부 API 를 권합니다. 이유는 비용입니다.** 여기서 모델이 하는 일은 짧은
문장 하나를 인자로 쪼개는 것뿐이라 프롬프트가 아주 짧습니다. 입력
200토큰·출력 50토큰으로 잡으면 (1,430원/달러 기준):

| 모델 | 100만 토큰당 입력/출력 | 추천 1건당 |
|---|---|---|
| Claude Opus 5 | $5 / $25 | 약 3.2원 |
| Claude Sonnet 5 | $3 / $15 (2026-08-31 까지 도입가 $2/$10) | 약 1.9원 |
| Claude Haiku 4.5 | $1 / $5 | 약 0.6원 |

한 달에 천 번을 써도 600~3,200원입니다. 이 돈을 아끼려고 추론 서버를
운영하는 것은 남는 장사가 아닙니다.

**모델을 고를 때 캐싱 최소 길이를 같이 봅니다.** 프롬프트 캐싱이 걸리는
최소 길이가 모델마다 다르고 **세대순이 아닙니다** — Opus 5 는 512토큰,
Haiku 4.5 는 4,096토큰입니다. 우리 도구 정의 프롬프트는 짧아서 Haiku 4.5
에서는 캐싱이 **조용히 안 걸립니다**(오류도 안 납니다). 싼 모델을 골랐다가
매번 전체 프롬프트를 새로 물어 되레 비싸질 수 있습니다.

**자체 설치가 말이 되는 경우는 하나뿐입니다** — 질의문을 밖으로 내보내지
않겠다는 것. 그런데 그것이 목적이라면 3단계 온디바이스가 더 낫습니다.
우리 서버에도 안 남으니까요. 그래서 자체 설치는 두 목적 어느 쪽에도
1등이 아닙니다.

### 7.1 갈아 끼울 자리

```java
interface IntentParser {
    Intent parse(String query, TripContext context);
}

record Intent(String locationQuery, String category, String keyword,
              Boolean openNow, Integer partySize) {
}
```

- `RuleIntentParser` — 1단계의 규칙. 모델 설정이 없으면 이것이 씁니다.
  **폴백이 아니라 기본값입니다.** 모델이 죽어도 추천은 계속 돕니다.
- `RemoteIntentParser` — `fit.ai.endpoint` 가 채워졌을 때만 뜹니다.

프롬프트는 원안 §5.1 의 도구 정의를 거의 그대로 씁니다. 다만 `required`
에 `location_query` 만 두는 원안과 달리, 우리는 여행 맥락에서 지역을 이미
알기 때문에 모델이 지역을 못 뽑아도 됩니다.

### 7.2 답변 합성은 하지 않습니다

원안 §5.4 는 2차 추론으로 자연어 문단을 만듭니다. 우리는 **하지 않습니다.**

FIT 의 화면은 문단이 아니라 카드와 지도입니다. 문단을 덧붙이면 (ㄱ) 읽는
시간이 늘고 (ㄴ) 카드에 이미 있는 평점·주소를 되풀이하고 (ㄷ) 무엇보다
지어낼 자리가 새로 생깁니다. 원안이 §5.4 에서 "Zero Hallucination" 을
프롬프트로 막으려 애쓰는데, **문단을 안 만들면 막을 것이 없습니다.**

한 줄짜리 요약이 필요해지면 그때 다시 봅니다.

### 7.3 무엇을 보내는가

모델에 보내는 것은 **질의문과 지역 이름뿐** 입니다. 좌표·`tripId`·사람 번호는
보내지 않습니다. 어디로 보내든 그쪽 로그에 남는다고 보고 그만큼만 실어
보냅니다.

## 8. 3단계 — 기기 안에서 돕니다

여기부터가 원안의 본론입니다. 값어치는 속도가 아니라 **질의문이 밖으로
나가지 않는다는 것** 입니다. "혼자 조용히 있고 싶은 곳" 은 우리 서버도
LLM 사업자도 알 필요가 없습니다.

### 8.1 먼저 알아야 할 것

- `frontend/` 에 `ios/`·`android/` 폴더가 **없습니다**. CNG 방식이고 빌드는
  EAS 입니다. 네이티브 모듈을 넣으려면 config plugin 을 함께 써야 하고,
  그 순간부터 **Expo Go 로는 못 봅니다.** 개발용 dev client 를 따로 구워야
  합니다. 팀의 개발 절차가 바뀌는 일이라 가장 먼저 합의할 것입니다.
- **웹에는 안 들어갑니다.** README 기준 실제 서비스는 nginx 가 내보내는 웹
  빌드이고, 거기서 1.1GB 모델은 성립하지 않습니다. 그래서 온디바이스는
  **웹과 앱을 가르는 첫 기능** 이 됩니다. 이 문서가 서버 경로를 끝까지
  살려 두는 이유가 그것입니다 — 갈라지는 것은 인자를 만드는 방법 하나로
  좁히고, 그 아래는 한 길로 둡니다.

### 8.2 모델

원안의 추천대로 **Qwen 2.5 1.5B Instruct, INT4** 를 첫 후보로 둡니다.
한국어와 JSON 구조 준수가 함께 필요한데 그 둘을 같이 만족하는 가장 작은
것입니다. 다만 원안의 별점표는 근거가 없으므로, 8.5 의 실측으로 대체합니다.

**번들에 넣지 않습니다.** 최초 실행 시 다운로드도 아닙니다 — 추천을
**처음 쓸 때** 받습니다. 여행 일정만 짜는 사람이 1.1GB 를 받을 이유가
없습니다. 받는 동안과 받기 전에는 2단계의 서버 경로로 돕니다.

### 8.3 붙이는 방법

```
frontend/modules/on-device-llm/     Expo Module (네이티브)
  android/        MediaPipe Tasks GenAI — LlmInference
  ios/            MediaPipe Tasks GenAI
  src/index.ts    ensureModel() · parseIntent() · unload()
  expo-module.config.json
app.config.js     plugin 등록 · 모델 저장 위치
```

화면은 네이티브를 직접 부르지 않습니다. `lib/intent.ts` 와
`lib/intent.web.ts` 두 짝으로 갈라, 웹 쪽은 그냥 `null` 을 돌려줍니다.
`lib/here.ts`·`here.web.ts` 와 `trip-map.tsx`·`trip-map.web.tsx` 가 이미
쓰는 방식이라 새 관습이 아닙니다.

`parseIntent()` 가 `null` 이면 화면은 서버에 문장을 그대로 보냅니다.
`Intent` 를 받으면 그것을 실어 보냅니다.

```
POST /api/trips/{tripId}/recommend
{ "query": "…", "intent": { "category": "bar", "keyword": "조용한" } }
```

서버는 `intent` 가 오면 자기 파서를 건너뜁니다. **그래도 검색은 서버가
합니다.** 3.1 의 규칙이 여기서도 유지됩니다.

`intent` 를 그대로 믿지는 않습니다. `category` 는 `PlaceKind.ALL` 안의
값인지 확인하고, `keyword` 는 길이를 자릅니다. 기기에서 온 값은 사람이
고칠 수 있는 값이라, 검증 없이 구글로 흘려보내면 우리 사용량으로 남의
질의를 대신 태우게 됩니다.

### 8.4 깨진 JSON

원안 §8-2 대로 정규식으로 중괄호 안쪽만 발라내고, 그래도 안 되면 `intent` 를
빼고 보냅니다. 즉 **1단계로 미끄러집니다.** 모델이 헛소리를 해도 사람이
보는 것은 조금 덜 맞는 추천이지 오류 화면이 아닙니다.

가능하면 constrained decoding(문법 제약)을 켜서 애초에 안 깨지게 합니다.
런타임이 지원하는지 8.5 에서 확인합니다.

### 8.5 하기 전에 재 볼 것

이 단계는 **실측 전에는 못 시작합니다.** 다음을 먼저 확인합니다.

1. Expo 57 / RN 0.86 에서 MediaPipe Tasks GenAI 가 붙는지, config plugin 만으로
   되는지
2. 중급 안드로이드(예: 갤럭시 A 계열)에서 1차 추론 실제 소요 시간
3. INT4 로딩 시 실제 RAM 점유와, 백그라운드에서 앱이 죽는 빈도
4. 한국어 질의 100건으로 JSON 구조 준수율과 인자 정확도. **2단계의
   서버 모델과 같은 100건으로 비교합니다.** 온디바이스가 눈에 띄게 못하면
   3단계를 접는 것이 맞습니다.
5. iOS 쪽 앱 크기 제한과 모델 파일의 저장 위치(백업 제외 지정 필요)

## 9. 약관과 개인정보

기존 판단을 그대로 잇습니다. 새로 생기는 것만 적습니다.

- **저장은 `placeId` 만.** 추천 결과를 우리 DB 에 쌓지 않습니다. 담기를
  누르는 순간에만 `SavedPlace`/`TripCandidate` 로 들어가고, 그때 저장되는
  값은 이미 정해진 그 모양입니다.
- **추천 결과 캐시는 메모리 · 짧게.** `PlaceInfoService` 의 한 시간 규칙을
  따릅니다.
- **구글 표기.** 추천 카드 목록 아래에도 출처 표시가 필요합니다. 지금
  장소 정보 화면에 있는 것과 같은 것을 씁니다.
- **질의문을 로그에 남기지 않습니다.** "혼자 울기 좋은 곳" 이 nginx 로그에
  남을 이유가 없습니다. 실패를 조사할 때는 질의문 대신 결과 개수와
  상태 코드만 남깁니다.

## 11. 순서와 의존

```
0단계 (Places New) ─┐
                    ├─→ 1단계 (맥락 추천) ─→ 2단계 (서버 LLM) ─┐
                    ┘                                          ├─→ 3단계 (온디바이스)
                                    8.5 실측 ──────────────────┘
```

- 0단계는 혼자서도 값이 있습니다. 다른 것이 다 엎어져도 해야 합니다.
- 1단계는 0단계 없이도 됩니다만, 레거시 API 위에 새 기능을 얹었다가 곧
  옮기는 것은 두 번 일입니다.
- 3단계는 **2단계가 먼저** 있어야 합니다. 비교 대상이 없으면 온디바이스가
  쓸 만한지 판단할 수 없고, 폴백도 없습니다.

## 12. 아직 모르는 것

- MediaPipe Tasks GenAI 를 Expo 57 CNG 에 붙이는 최신 방법 (8.5-1)
- 2단계에서 어느 모델을 쓸지 — 외부 API 로 간다는 것까지는 정했습니다(7.0).
  세 후보의 값과 캐싱 최소 길이는 7.0 에 적었고, 고르는 것은 8.5-4 의
  질의 100건으로 정확도를 재 본 뒤입니다
- 추천 결과를 지도에 미리 찍어 줄지, 카드만 줄지 — 화면을 그려 보고 정합니다
- 한 번에 몇 개를 보여 줄지. 검색은 여섯입니다(`PlaceSearchService.LIMIT`).
  추천은 고르는 일이라 더 적어야 할 수도 있습니다
